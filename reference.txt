================================================================================
RiskSequencer - Project Reference & Interview Prep
Behavioral fraud detection: LSTM + LightGBM hybrid, with a full MLOps loop
================================================================================

This document explains the project end to end: what it is, why it matters, a
plain-English walkthrough of what happens when, the architecture, why we chose
each model, notes on Evidently AI, the real problems we hit and fixed, the
results, and interview questions with answers.

--------------------------------------------------------------------------------
1. WHAT THE PROJECT IS (ONE PARAGRAPH)
--------------------------------------------------------------------------------
RiskSequencer scores a user's fraud RISK by looking at SEQUENCES OF BEHAVIOR OVER
TIME, not one transaction in isolation. A single action (a device change, a new
country, a big purchase) can look fine alone, but a PATTERN of actions - device
change -> address update -> burst of fast transactions - is the signature of an
account takeover. We model that pattern with a 2-layer LSTM + attention, combine
it with a LightGBM model on rich tabular features, and wrap everything in an
MLOps loop: experiment tracking (MLflow), a real-time serving endpoint (AWS
SageMaker), drift monitoring (Evidently AI), Slack alerting, and automated
retraining (Airflow) with a promotion gate.

--------------------------------------------------------------------------------
2. WHY IT MATTERS (THE BUSINESS FRAMING)
--------------------------------------------------------------------------------
Fraud detection is a cost-asymmetry problem. Two errors cost money in opposite
directions:
  - False negative (missed fraud)        -> you lose the fraud amount.
  - False positive (block a real user)   -> churn + manual-review cost.

Accuracy is useless here: fraud is ~1-3% of transactions, so "never fraud" scores
97-99% accuracy and catches nothing. So we use the RIGHT metrics (AUC-ROC,
precision at a fixed low false-positive rate) and DOLLARS (a business-metrics
module computes $ fraud caught, $ false-positive cost, net savings, and a profit
curve that finds the threshold that maximizes net savings - usually NOT the same
threshold as "5% FPR").

Why sequences: modern account-takeover fraud is designed to beat per-transaction
rules. Each step looks legitimate; the fraud only shows up in the ORDER and TIMING
of events. That is exactly what a sequence model with attention exposes - and the
attention weights tell an analyst WHICH past events caused the flag.

3. EASY ENGLISH: WHAT HAPPENS WHEN  (say this to an interviewer)
--------------------------------------------------------------------------------

THERE ARE THREE STORIES. Tell them as three simple flows.

--- STORY A: "A transaction comes in - how do we score it?" (inference) ---------
  1. A user makes a transaction.
  2. We pull that user's recent transaction history (their last 50 events).
  3. We turn that history into numbers (features): how fast are they spending,
     is this a new device or country, is the amount unusual for them, etc.
  4. Two models look at it:
       - The LSTM reads the SEQUENCE of those 50 events in order and asks "does
         this pattern look like an account takeover?"
       - LightGBM looks at the rich per-transaction details and asks "does this
         single transaction look fraudulent?"
  5. A small combiner (the stacking model) merges the two opinions into one
     fraud probability between 0 and 1.
  6. If the probability is above our chosen threshold, we flag it as fraud.
  7. We also return the attention weights - basically "we flagged this because
     of these specific recent events" - so a human can audit the decision.
  All of this runs on a SageMaker endpoint and the model itself answers in about
  45 milliseconds.

--- STORY B: "How do we keep the model from going stale?" (the MLOps loop) ------
  Fraud patterns change over time, so a model that was great last month can rot.
  Every week, Airflow (a scheduler) wakes up automatically and:
  1. Evidently AI compares recent behavior to a reference period and asks "have
     the important features drifted?" using a number called PSI.
  2. If PSI goes above 0.20 on any of our 3 watched features, that means behavior
     has shifted enough to matter -> trigger a retrain. (If nothing drifted, it
     stops and does nothing - no wasted compute.)
  3. We retrain the model on fresh data.
  4. We check the new model: it must beat a minimum quality bar (AUC >= 0.90) AND
     beat the current production model (champion vs challenger). No human approval
     needed; the gate is automatic and has no manual override.
  5. If it passes, we package it and it can go live. If it fails, we keep the old
     model.
  6. Slack gets a message at each important step (drift found, retrain done,
     gate passed/failed). Nobody has to babysit it.

--- STORY C: "How is it deployed?" (serving) ------------------------------------
  We bundle the trained model + its scaler + its decision threshold + the
  inference code into one file (model.tar.gz), upload it to S3, and SageMaker
  serves it as a real-time HTTP endpoint. We load-tested it and the model's own
  inference time (p99) was 45 ms, under our 50 ms target.

ONE-LINER YOU CAN SAY: "It's a fraud model that reads a user's recent behavior as
a sequence, combines a deep sequence model with a gradient-boosted model, serves
predictions in ~45ms on SageMaker, and retrains itself automatically when
Evidently detects the data has drifted."

5. WHY EACH MODEL - LSTM, LIGHTGBM, AND THE HYBRID
--------------------------------------------------------------------------------

5.1 WHY AN LSTM (+ ATTENTION)
  - The hypothesis is sequential: fraud is a pattern across a user's recent
    transactions. An LSTM processes an ordered, variable-length sequence and
    carries state, so it can learn "device change THEN burst" relationships a
    one-row model cannot.
  - Attention is mandatory (explainability is a hard requirement). It gives a
    weight per timestep; the weighted sum feeds the classifier, and the weights
    are the explanation - "flagged because of these past events."
  - We mask padding so attention ignores the zero-padded positions of short
    histories.

5.2 WHY A LIGHTGBM BASELINE / LAYER
  - Gradient-boosted trees are the workhorse for TABULAR fraud data: mixed
    numeric/categorical features, native missing-value handling, strong with
    class imbalance (scale_pos_weight), fast and accurate.
  - A fair, hard-to-beat baseline: if a sequence model can't beat a boosted tree,
    the complexity isn't justified.
  - Free SHAP explanations (per-feature attributions).

5.3 WHY THE HYBRID (AND WHY STACKING)
  - On REAL IEEE-CIS data the LSTM alone reached only ~0.81 AUC. We proved this
    was a FEATURE problem, not a model problem: our pipeline used ~9 of 394
    columns and dropped the C/D/V engineered features that carry the signal. A
    quick LightGBM on the native features beat the LSTM by 7+ points.
  - Also a STRUCTURAL mismatch: IEEE-CIS is per-transaction; the card1+addr1 user
    proxy gives a median of 2 transactions per user, so the LSTM has almost no
    sequence to learn from.
  - Fix = the hybrid from the system-prompt design. LightGBM captures the rich
    tabular signal; the LSTM captures the (smaller) sequence signal; a STACKING
    META-LEARNER (logistic regression) learns how to weight them. We aggregate
    LightGBM's per-transaction scores to the user level with MAX ("fraud anywhere
    in the window"), align with the LSTM's per-user scores, fit the meta-learner
    ON THE VALIDATION split (not train - that's what makes it leak-free stacking),
    and evaluate on the held-out test split.
  - Result: hybrid 0.929, with the LSTM adding real lift on top of LightGBM.

6. NOTES ON EVIDENTLY AI (the drift-monitoring piece)
--------------------------------------------------------------------------------

WHAT IT IS
  Evidently AI is an open-source library for monitoring ML data and models in
  production. Its core idea: compare a REFERENCE dataset (what the model was
  trained on / a healthy baseline) against a CURRENT dataset (recent live data)
  and report whether things have DRIFTED.

WHAT "DRIFT" MEANS
  Data drift = the input distribution today no longer looks like the data the
  model learned from. Example: if "transactions per hour" suddenly spikes across
  many users, the model is now seeing inputs it wasn't trained for, and its
  predictions get less reliable. Drift is an EARLY WARNING that the model may be
  going stale - you act before accuracy visibly drops.

HOW WE USE IT (concretely)
  - We run Evidently's DataDriftPreset with the PSI statistical test.
  - PSI (Population Stability Index) is a single number for how much one feature's
    distribution shifted. Rule of thumb: < 0.1 = stable, 0.1-0.2 = moderate,
    > 0.2 = significant drift. We use a 0.20 threshold.
  - We monitor exactly 3 behavioral features: txn_velocity_1h, amount_zscore,
    new_device_flag. (Focused set = clean signal, low alert noise.)
  - If ANY of the 3 crosses PSI 0.20, we trigger retraining and a Slack alert.
  - Evidently can also produce a rich HTML drift report for a dashboard.

WHY EVIDENTLY INSTEAD OF JUST COMPUTING PSI OURSELVES
  We actually do both: Evidently is the primary engine (industry-standard,
  produces shareable reports, supports many drift tests), and we keep a small
  hand-rolled PSI as a dependency-free FALLBACK so the trigger logic stays
  testable in environments where Evidently isn't installed (e.g. CI).

HOW PSI IS COMPUTED (so you can explain it)
  Bucket the reference values into bins. For each bin compute the % of reference
  points and the % of current points. PSI = sum over bins of
  (cur% - ref%) * ln(cur% / ref%). Bigger = more shift. It's symmetric-ish and
  punishes bins that grew or shrank a lot.

7. THE BUILD, PHASE BY PHASE
--------------------------------------------------------------------------------
Phase 0 - Environment & structure: config.py as the single source of truth for
  the hard constants (sequence length = 50, PSI = 0.20, MLflow AUC gate = 0.90,
  the 3 monitored features), repo layout, CI (GitHub Actions runs the tests on
  every PR), branch protection.

Phase 1 - Data & features: a synthetic generator (runs with zero setup), an
  IEEE-CIS adapter (maps the real Kaggle data to one canonical schema; rebuilds
  the missing user_id and timestamp), a CAUSAL feature pipeline (no leakage), a
  sequence builder ((N,50,F) left-padded + mask), and a TIME-BASED split.

Phase 2 - Modeling: the LSTM+attention, the LightGBM baseline, the HYBRID
  stacking ensemble, the training loop (BCEWithLogitsLoss + pos_weight, AdamW,
  ReduceLROnPlateau, early stopping on val AUC), evaluation + threshold tuning,
  and a hyperparameter search.

Phase 3 - Explainability & evaluation: attention visualization, SHAP for
  LightGBM, error analysis (false-negative vs false-positive profiling), and a
  business-metrics module ($ caught / FP cost / net savings + profit curve).

Phase 4 - Deployment: SageMaker inference handlers (model_fn/input_fn/predict_fn/
  output_fn) with train/serve scaler parity, an MLflow promotion gate (no manual
  override), a packaging script (model.tar.gz), AND a real deploy+benchmark
  script that stood up a live endpoint, measured p99, and tore it down.

Phase 5 - Monitoring & retraining: Evidently AI drift (PSI, threshold 0.20),
  Slack alerting, a runnable Airflow DAG (@weekly, drift-triggered, runs the full
  loop end-to-end), and a champion/challenger + AUC-gate promotion decision.

8. PROBLEMS WE FACED AND HOW WE SOLVED THEM (THE GOOD STORIES)
--------------------------------------------------------------------------------

8.1 THE REAL-DATA REALITY CHECK (the big one)
  Synthetic data gave ~0.99 AUC; real IEEE-CIS gave 0.81 for the LSTM. Instead of
  panic-tuning, we DIAGNOSED: a quick LightGBM on native features hit 0.888,
  proving the gap was features/data framing, not the model. That led to the
  hybrid (0.81 -> 0.92), then feature enrichment with the identity table +
  categoricals (-> 0.929). Lesson: isolate WHERE the signal is before changing
  the model.

8.2 THE 0.94 TARGET vs DATASET REALITY
  The 0.94 target assumed a sequence-friendly dataset. IEEE-CIS is
  per-transaction; the user proxy gives a median of 2 transactions per user. We
  made the honest call to hold at 0.929 rather than chase the last point with
  leaky, dataset-specific feature engineering. Knowing when a number stops being
  worth the effort is a real skill.

8.3 THE OPENMP SEGFAULT (a nasty hidden bug)
  Training PyTorch and LightGBM in the SAME process segfaulted on macOS - both
  bundle their own OpenMP runtime and they conflict. It was invisible because no
  single test loaded both. Fix: set OMP_NUM_THREADS=1 and KMP_DUPLICATE_LIB_OK=
  TRUE before importing either library, single-thread both, and lock it in with a
  SUBPROCESS regression test so a crash can't kill the whole suite. The hybrid
  trainer needs both libs, so this guard is load-bearing.

8.4 THE PANDAS 3.0 DTYPE TRAP
  Our categorical detection used `dtype == object`, but pandas 3.0 reads strings
  as the new `str` dtype, so ZERO categoricals were detected and the identity
  features were silently ignored. Fix: detect categoricals by "not numeric." The
  dangerous bugs are the silent ones - no error, just worse results.

8.5 THE SAGEMAKER SDK + GEVENT INSTALL ISSUES
  The SageMaker SDK v3 is a rewrite that moved modules and broke the classic
  PyTorchModel deploy path, so we pinned to v2.x. And `gevent` (a transitive dep)
  wouldn't build from source, so we installed it from a prebuilt wheel. Lesson:
  pin to the API you actually wrote against; don't fight source builds when a
  wheel exists.

8.6 MEASURING p99 LATENCY HONESTLY
  Measuring from a laptop gives ~200ms round-trip - but that's mostly NETWORK to
  us-east-1, not inference. The honest "inference latency" is SageMaker's
  CloudWatch ModelLatency metric, which excludes client/network time. That came
  out p99 = 45ms (< 50ms). Always measure the right thing.

8.7 DATA LEAKAGE - AVOIDED BY DESIGN
  Three places we could have leaked and didn't: (a) causal features (expanding+
  shift, first-seen flags); (b) a TIME-BASED split, never random; (c) the
  stacking meta-learner fit on VALIDATION predictions, not training predictions.

8.8 RESUME-HONESTY PASS
  We deliberately verified each claim against reality: validated the hybrid on
  real data (0.93), wired Evidently for real (not just hand-rolled PSI), made the
  Airflow DAG actually run end-to-end, and deployed a real SageMaker endpoint to
  measure p99 (45ms). The bullets are backed by evidence, not aspiration.

10. KEY DESIGN DECISIONS (QUICK REFERENCE)
--------------------------------------------------------------------------------
  - Output LOGITS, not sigmoid -> BCEWithLogitsLoss for numerical stability;
    apply sigmoid only at inference.
  - pos_weight in the loss for imbalance instead of blindly oversampling (SMOTE).
  - Left-pad short histories + mask -> the most recent transaction is always at
    the same position, and attention ignores padding.
  - Aggregate LightGBM per-transaction scores to the user with MAX.
  - Fit the stacker on validation, evaluate on test (leak-free stacking).
  - Scaler fit on TRAIN only, reused at val/test/serve (parity, no leakage).
  - Evidently AI primary + hand-rolled PSI fallback (testable without the dep).
  - Always-teardown deployment script (finally block) so nothing lingers billing.

11. INTERVIEW QUESTIONS (with answers)
================================================================================

Q1. Why a sequence model instead of classifying each transaction independently?
  The fraud signal lives in the ORDER and TIMING of events. Account takeover is
  built from individually-plausible steps. A per-transaction classifier sees each
  step in isolation and misses the pattern. An LSTM carries state across the
  sequence and represents "event B is suspicious GIVEN event A happened recently."

Q2. Walk me through the attention mechanism and why it's required.
  Score each LSTM hidden state with a linear layer, mask padded timesteps
  (set their score very negative so softmax ~0), softmax over real timesteps,
  weighted-sum the hidden states into a context vector for the classifier. It's
  required because explainability is mandatory: the weights say WHICH past
  transactions drove the flag.

Q3. How do you prevent data leakage in a fraud time series?
  Causal features (amount z-score = expanding().mean().shift(1); "new device" =
  first-seen flag); a TIME-BASED split (train on earliest window, test on later);
  and the stacking meta-learner fit on the validation split, not the training
  split. Scaler fit on train only.

Q4. Class imbalance is ~3% fraud. Why pos_weight instead of SMOTE?
  pos_weight (neg/pos) in BCEWithLogitsLoss reweights the loss so positives count
  more without fabricating synthetic minority points. SMOTE interpolates fake
  fraud in feature space, which is unrealistic for behavioral/sequential data and
  awkward with sequences.

Q5. Why 0.99 on synthetic but 0.81 (LSTM) on real data?
  Synthetic fraud is a clean, separable burst. Real fraud is subtle, and our
  adapter used ~9 of 394 columns, dropping the engineered features that carry the
  signal; plus the user proxy gives ~2 txns/user, starving the LSTM. We proved it
  was features/framing by training a quick LightGBM that beat the LSTM by 7+ AUC.

Q6. Why combine LightGBM and the LSTM? Why stacking?
  They capture complementary signal: LightGBM is best for rich tabular features;
  the LSTM adds the sequence signal LightGBM can't see. We stack with a logistic
  meta-learner so the weighting is LEARNED, fit on validation to avoid leakage.
  The hybrid beat LightGBM alone, so the LSTM adds non-redundant signal.

Q7. How do you align a per-transaction LightGBM with a per-user LSTM for stacking?
  The unit is the user (label = fraud anywhere in their window). LightGBM scores
  each transaction; we aggregate to one score per user with MAX. The LSTM already
  outputs one score per user. Align both on the user set, then stack.

Q8. AUC-ROC is your headline metric. Right choice for 3% fraud? What else?
  AUC is threshold-independent and good for ranking but can look optimistic under
  heavy imbalance. So we also track average precision (PR-AUC), precision at a
  fixed low FPR, and dollar metrics. For deployment the operating threshold
  matters more than AUC, so we tune it explicitly.

Q9. Your threshold tuning gave precision 1.0 but recall ~0. Why, and the fix?
  "Maximize precision subject to FPR <= 5%" can collapse to an extreme threshold
  flagging almost nothing. We surfaced it and added a profit curve (net savings vs
  threshold) so we choose the operating point on business value; in production
  we'd cap minimum recall or optimize expected cost directly.

Q10. Explain the torch + LightGBM segfault and your fix.
  Both bundle their own OpenMP runtime; loading both in one process on macOS
  conflicts and segfaults. It was hidden because no single test imported both. Fix:
  OMP_NUM_THREADS=1 + KMP_DUPLICATE_LIB_OK=TRUE before importing, single-thread
  both, and a subprocess regression test so a crash can't fail the whole suite.

Q11. Why logits + BCEWithLogitsLoss instead of Sigmoid + BCELoss?
  BCEWithLogitsLoss fuses sigmoid and loss in a numerically stable way (log-sum-
  exp), avoids overflow/vanishing gradients at saturated probabilities, and is
  where pos_weight is applied cleanly. The model emits logits; we apply sigmoid
  only at inference.

Q12. What is Evidently AI and how does it trigger retraining?
  Evidently is an ML monitoring library that compares a reference dataset to
  current data and reports drift. We run its DataDriftPreset with the PSI test on
  3 behavioral features; if any feature's PSI exceeds 0.20 we trigger retraining
  and a Slack alert. We keep a hand-rolled PSI as a dependency-free fallback so
  the logic is testable without Evidently installed.

Q13. What is PSI and how is it computed?
  Population Stability Index - how much a feature's distribution shifted vs a
  baseline. Bin the reference values; for each bin take reference% and current%;
  PSI = sum((cur% - ref%) * ln(cur% / ref%)). < 0.1 stable, 0.1-0.2 moderate,
  > 0.2 significant. We trigger at 0.20.

Q14. What is champion/challenger and how does promotion work?
  The production model is the champion. A newly trained challenger must pass TWO
  gates: an absolute AUC gate (>= 0.90, no manual override) AND beat the champion's
  AUC. In production it also gets shadow/A-B traffic before full promotion. One
  decide_promotion() function enforces both and is shared by the local pipeline
  and the Airflow DAG so they can't disagree.

Q15. Why left-pad and mask, not right-pad?
  Left-padding puts the most recent transaction at the last position for every
  user, so "position" has consistent temporal meaning regardless of history
  length. The mask makes the LSTM/attention ignore the zero rows so short
  histories aren't polluted by fake transactions.

Q16. How did you deploy and verify p99 < 50ms? What's the subtlety?
  Packaged model + scaler + threshold + inference code into model.tar.gz, uploaded
  to S3, deployed a SageMaker PyTorch real-time endpoint, and load-tested it. The
  subtlety: measuring from a laptop includes ~200ms of NETWORK round-trip to
  us-east-1. The honest inference latency is CloudWatch ModelLatency (excludes
  network), which was p99 = 45ms. Then I tore the endpoint down so nothing bills.

Q17. The card1+addr1 user id is a proxy. Dangers and alternatives?
  It's imperfect: collisions (a popular card1 with missing addr1 collapses many
  users into one mega-user with thousands of transactions) and short histories
  (~2 txns/user), which starves the sequence model. Alternatives: a stronger uid
  (card + addr + a registration-day-derived key), or accept the dataset is
  per-transaction and lean on the tabular model. In production you'd use a real
  account id and the sequence model would be much stronger.

Q18. Walk me through the automated retraining loop end to end.
  Airflow runs weekly. check_drift uses Evidently PSI; if no feature breaches 0.20
  the run short-circuits (no retrain). If drift is detected, retrain on fresh data,
  then the promotion gate checks AUC >= 0.90 AND beats champion; if it passes, the
  model is packaged for deployment, else the old model stays. Slack alerts fire at
  drift, completion, and failure; MLflow logs every run; each task has 3 retries.
  I demonstrated the whole loop running end-to-end with no manual steps.

Q19. (Stretch) How would you push 0.929 toward 0.94 responsibly?
  Add uid-aggregation features (per-user amount mean/std/count, inter-arrival
  stats) and D-feature day-normalization - the highest-impact IEEE-CIS techniques.
  The catch: as GLOBAL aggregations they LEAK; done correctly you compute stats on
  the train split only and map them forward with a cold-start fallback. I judged
  0.929 strong enough that the last point wasn't worth leak-prone, dataset-
  specific engineering - a real tradeoff call, not a number chase.
