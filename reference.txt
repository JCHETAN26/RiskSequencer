================================================================================
RiskSequencer — Project Reference & Interview Prep
Behavioral fraud detection: LSTM + LightGBM hybrid, with a full MLOps loop
================================================================================

This document explains the project end to end: what it is, why it matters, the
decisions behind the modeling, the real problems we hit and how we solved them,
the results, and a set of interview questions with answers.

--------------------------------------------------------------------------------
1. WHAT THE PROJECT IS (THE ONE-PARAGRAPH VERSION)
--------------------------------------------------------------------------------
RiskSequencer is a production-style fraud-detection system that scores a user's
RISK by looking at SEQUENCES OF BEHAVIOR OVER TIME, not just one transaction in
isolation. The core idea: a single action (a device change, a new country, a
large purchase) can look fine on its own, but a PATTERN of actions — device
change -> address update -> burst of rapid transactions — is the signature of an
account takeover. We model that pattern with a 2-layer LSTM + attention, combine
it with a LightGBM model on rich tabular features, and wrap the whole thing in an
MLOps loop: experiment tracking (MLflow), a real-time serving path (SageMaker
handlers), drift monitoring (PSI / Evidently), Slack alerting, and automated
retraining (Airflow) with a champion/challenger promotion gate.

--------------------------------------------------------------------------------
2. WHY IT MATTERS (THE BUSINESS FRAMING)
--------------------------------------------------------------------------------
Fraud detection is a cost-asymmetry problem. Two kinds of error cost money in
opposite directions:
  - False negative (missed fraud) -> you eat the fraud amount ($).
  - False positive (blocking a legit customer) -> churn + manual-review cost.

A model that "looks good" on accuracy is useless here because fraud is ~1-3% of
transactions; predicting "never fraud" is 97-99% accurate and catches nothing.
So the project is framed around the RIGHT metrics (AUC-ROC, precision at a fixed
low false-positive rate) and around DOLLARS (we built a business-metrics module:
$ fraud caught, $ false-positive cost, net savings, and a profit curve that finds
the threshold maximizing net savings — which is usually NOT the same threshold as
"FPR <= 5%").

Why "sequence" framing matters: modern account-takeover fraud is specifically
designed to defeat per-transaction rules. Each step is individually plausible.
The fraud only becomes visible in the ORDER and TIMING of events. That is exactly
what a sequence model with attention is built to expose — and, as a bonus, the
attention weights tell a fraud analyst WHICH past events drove the flag.

--------------------------------------------------------------------------------
3. THE PROBLEM WE ACTUALLY SOLVED
--------------------------------------------------------------------------------
Concretely we built an end-to-end, tested, reproducible pipeline that:
  - Turns raw transactions into causally-correct (no-leakage) features.
  - Builds left-padded (N, 50, F) per-user sequence tensors with a padding mask.
  - Trains an LSTM+attention model and a LightGBM model.
  - Combines them with a stacking meta-learner into a hybrid.
  - Evaluates honestly on a TIME-BASED held-out split (no future leakage).
  - Packages a deployable model.tar.gz for SageMaker.
  - Detects drift (PSI), alerts on Slack, and retrains automatically with a
    promotion gate (absolute AUC gate + champion/challenger comparison).

And critically: we VALIDATED IT ON REAL DATA (IEEE-CIS, ~590K transactions), not
just a toy generator. That validation is where the most interesting engineering
lessons came from (see section 6).

--------------------------------------------------------------------------------
4. WHY EACH MODEL — LSTM, LIGHTGBM, AND THEN THE HYBRID
--------------------------------------------------------------------------------

4.1 WHY AN LSTM (+ ATTENTION)
  - The hypothesis is sequential: fraud is a pattern across a user's recent
    transactions. An LSTM processes a variable-length, ordered sequence and
    carries state, so it can learn "device change THEN burst" relationships that
    a model seeing one row cannot.
  - Attention is MANDATORY in this project (explainability is a hard
    requirement). Additive attention produces a weight per timestep; the weighted
    sum is the context vector fed to the classifier. Those weights are the
    explanation: "this sequence was flagged because of these specific past
    events." We return (logits, attention_weights) from forward().
  - We use a padding MASK so the attention never attends to the zero-padded
    positions of short histories.

4.2 WHY A LIGHTGBM BASELINE
  - Gradient-boosted trees are the workhorse for TABULAR fraud data. They handle
    mixed numeric/categorical features, missing values natively, and heavy class
    imbalance (scale_pos_weight), and they train fast and strong.
  - It is a fair, hard-to-beat BASELINE: if a fancy sequence model can't beat a
    boosted tree, the sequence framing isn't earning its complexity. The plan
    explicitly wanted the LSTM to beat LightGBM by >= 4 AUC points to justify
    itself.
  - LightGBM also gives SHAP explanations for free (per-feature attributions).

4.3 WHY THE HYBRID (AND WHY STACKING)
  - When we validated on REAL IEEE-CIS data, the LSTM alone hit only ~0.81 AUC,
    far below the 0.94 target. Diagnosis (we proved it): NOT a model problem — a
    FEATURE problem. Our behavioral feature pipeline used ~9 of the 394 columns,
    discarding the C/D/V engineered features where IEEE-CIS's signal actually
    lives. A throwaway LightGBM on the native features beat the LSTM by 7+ points.
  - Also a STRUCTURAL mismatch: IEEE-CIS is fundamentally per-transaction. With a
    card1+addr1 user proxy, the median user has only 2 transactions, so the
    sequence model has almost nothing to "sequence."
  - The fix is the architecture from the system prompt: a HYBRID. LightGBM
    captures the rich tabular signal; the LSTM captures the (smaller) sequential
    signal; a STACKING META-LEARNER (logistic regression) learns how to weight
    the two. We aggregate LightGBM's per-transaction scores to the user level
    with MAX ("fraud anywhere in the window"), align them to the LSTM's per-user
    scores, fit the meta-learner ON THE VALIDATION SPLIT (so it never sees data
    the base models trained on — this is what makes it proper stacking and not
    leakage), and evaluate on the held-out test split.
  - Result: hybrid reached 0.929, with the LSTM contributing a real (if small)
    lift on top of LightGBM.

--------------------------------------------------------------------------------
5. THE BUILD, PHASE BY PHASE
--------------------------------------------------------------------------------
Phase 0 - Environment & structure: config.py as the single source of truth for
  the hard constants (sequence length = 50, PSI threshold = 0.20, MLflow AUC gate
  = 0.90, the three monitored drift features), repo layout, requirements, CI.

Phase 1 - Data & features:
  - A SYNTHETIC generator that injects fraud as a behavioral burst, so the whole
    pipeline runs with zero external dependencies.
  - An IEEE-CIS ADAPTER mapping the Kaggle dataset to one canonical schema, so all
    downstream code is dataset-agnostic. It reconstructs the two things IEEE-CIS
    lacks: a timestamp (TransactionDT anchored to a reference date) and a user_id
    (card1+addr1 proxy).
  - A CAUSAL feature pipeline (velocity, time gaps, amount z-score, first-seen
    flags) where every feature uses only the current and EARLIER rows (e.g.
    amount z-score = expanding().mean().shift(1)) so nothing leaks the label.
  - A sequence builder producing left-padded (N, 50, F) tensors + a padding mask,
    and a TIME-BASED train/val/test split.

Phase 2 - Modeling: the RiskSequencer LSTM+attention, the LightGBM baseline, the
  training loop (BCEWithLogitsLoss with pos_weight, AdamW, ReduceLROnPlateau,
  early stopping on validation AUC), evaluation + threshold tuning, and a
  hyperparameter search.

Phase 3 - Explainability & evaluation: attention-weight visualization notebook,
  SHAP for LightGBM, ERROR ANALYSIS (false-negative vs false-positive profiling),
  and a BUSINESS-METRICS module ($ caught / FP cost / net savings + profit curve).

Phase 4 - Deployment: SageMaker inference handlers (model_fn/input_fn/predict_fn/
  output_fn) with train/serve scaler parity, an MLflow promotion gate (no manual
  override), and a packaging script that bundles model + scaler + threshold +
  code into a deployable model.tar.gz.

Phase 5 - Monitoring & retraining: PSI drift detection on the three monitored
  features, Slack alerting, an Airflow retrain DAG, and a LOCAL, testable retrain
  orchestration (drift -> retrain -> evaluate -> promotion decision -> package)
  with a champion/challenger gate.

--------------------------------------------------------------------------------
6. PROBLEMS WE FACED AND HOW WE SOLVED THEM (THE GOOD STORIES)
--------------------------------------------------------------------------------

6.1 THE REAL-DATA REALITY CHECK (the big one)
  Synthetic data gave ~0.99 AUC; real IEEE-CIS gave 0.81. Rather than panic-tune
  the model, we DIAGNOSED: a quick LightGBM on the native features hit 0.888,
  proving the gap was features/data framing, not the model. That led to the
  hybrid (0.81 -> 0.922), then feature enrichment (identity + categoricals ->
  0.929). Lesson: when a model underperforms, isolate WHERE the signal is before
  changing the model.

6.2 THE 0.94 TARGET vs DATASET REALITY
  The 0.94 target assumed a sequence-friendly dataset. IEEE-CIS is
  per-transaction; the card1+addr1 proxy yields a median of 2 transactions per
  user. We made the honest call to hold at 0.929 rather than chase the last point
  with leaky, dataset-specific Kaggle feature engineering. Lesson: know when a
  benchmark number stops being worth the engineering.

6.3 THE OPENMP SEGFAULT (a genuinely nasty bug)
  Training PyTorch and LightGBM IN THE SAME PROCESS segfaulted on macOS, because
  both libraries bundle their own OpenMP runtime and the two conflict. It was
  invisible because no single test loaded both libraries together. Fix: set
  OMP_NUM_THREADS=1 and KMP_DUPLICATE_LIB_OK=TRUE BEFORE importing either library,
  single-thread both, and lock it in with a SUBPROCESS regression test (so a crash
  can't take down the whole test suite). The hybrid trainer needs both in one
  process, so this guard is load-bearing.

6.4 THE PANDAS 3.0 DTYPE TRAP
  Our categorical detection used `dtype == object`, but pandas 3.0 reads strings
  as the new `str` dtype, so ZERO categoricals were detected and the identity
  features were silently ignored. Fix: detect categoricals by "not numeric"
  instead of "== object." Lesson: silent correctness bugs (no error, just worse
  results) are the dangerous ones — sanity-check feature counts.

6.5 DATA LEAKAGE — AVOIDED BY DESIGN
  Three places we could have leaked and didn't: (a) features are causal
  (expanding+shift, first-seen flags); (b) the split is TIME-BASED, never random;
  (c) the stacking meta-learner is fit on the VALIDATION predictions, not the
  training predictions. Random splits or in-sample stacking would have inflated
  AUC and lied to us.

6.6 THRESHOLD DEGENERACY
  "Maximize precision subject to FPR <= 5%" can collapse to a threshold that
  flags almost nothing (precision 1.0, recall ~0). We surfaced this and built a
  PROFIT CURVE (net savings vs threshold) so the operating point is chosen on
  business value, not a degenerate corner.

6.7 THE ENGINEERING/GIT WORKFLOW HICCUPS
  Real-world friction we worked through: an empty GitHub repo with no base branch
  (so no PR was possible until we bootstrapped main); a read-only access token
  (push 403s despite admin role on the repo); branch protection requiring a review
  that a solo dev can't self-approve (solved with admin-merge, then by dropping
  required reviews to 0 while keeping the CI gate and no-direct-push rule). Lesson:
  branch protection + required status checks are the cheap insurance that keeps
  main green.

--------------------------------------------------------------------------------
7. RESULTS (REAL IEEE-CIS, HELD-OUT TEST, USER-LEVEL AUC)
--------------------------------------------------------------------------------
  LSTM + attention alone .................. 0.812
  LightGBM alone (native+identity+cats) ... 0.926
  HYBRID (stacked meta-learner) ........... 0.929   <-- shipped
  (Synthetic generator, LSTM alone ........ ~0.99, because fraud is separable.)

  Hard constants enforced in code: sequence length = 50, pos_weight for
  imbalance, PSI = 0.20 on exactly {txn_velocity_1h, amount_zscore,
  new_device_flag}, MLflow AUC gate = 0.90 with no manual override, time-based
  splits, champion/challenger before promotion.

--------------------------------------------------------------------------------
8. KEY DESIGN DECISIONS (QUICK REFERENCE)
--------------------------------------------------------------------------------
  - Output LOGITS, not sigmoid, from the model -> use BCEWithLogitsLoss for
    numerical stability; apply sigmoid only at inference.
  - pos_weight in the loss for imbalance instead of blindly oversampling (SMOTE).
  - Left-pad (not right-pad) short histories + mask -> the most RECENT
    transaction is always at the same position, and attention ignores padding.
  - Aggregate LightGBM per-transaction scores to the user with MAX (matches the
    "fraud anywhere in the window" label).
  - Fit the stacker on validation, evaluate on test (proper stacking).
  - RobustScaler fit on TRAIN only, reused at val/test/serve (parity, no leakage).

9. INTERVIEW QUESTIONS (with answers)
================================================================================

Q1. Why a sequence model instead of classifying each transaction independently?
  Because the fraud signal lives in the ORDER and TIMING of events. Account
  takeover is built from individually-plausible steps (login from new device,
  address change, then a burst). A per-transaction classifier sees each step in
  isolation and misses the pattern. An LSTM carries state across the sequence and
  can represent "event B is suspicious GIVEN event A happened recently."

Q2. Walk me through the attention mechanism and why it's required here.
  We score each LSTM hidden state with a linear layer (additive attention),
  mask out padded timesteps (set their score to -1e9 so softmax -> ~0), softmax
  over real timesteps to get weights, and take the weighted sum of hidden states
  as the context vector for the classifier. It's required because explainability
  is a hard requirement: the weights tell an analyst WHICH past transactions drove
  the flag. Without it the model is an opaque score.

Q3. How do you prevent data leakage in a fraud time series?
  Three layers. (1) Causal features: every feature uses only current and earlier
  rows — e.g. amount z-score is expanding().mean().shift(1), "new device" is a
  first-seen flag via duplicated(). (2) Time-based split: train on the earliest
  window, validate/test on later windows; never a random split, which would let
  the model "see the future." (3) Stacking meta-learner fit on the validation
  split, not the training split, so it never learns from rows the base models
  were trained on. We also fit the scaler on train only.

Q4. Class imbalance is ~3% fraud. Why pos_weight instead of SMOTE/oversampling?
  pos_weight (neg/pos) in BCEWithLogitsLoss reweights the loss so positives count
  more, WITHOUT fabricating synthetic minority examples. SMOTE interpolates new
  fraud points in feature space, which for sequential/behavioral data can create
  unrealistic samples and leak structure; it's also awkward with sequences. The
  plan made pos_weight the default and required justification before oversampling.

Q5. Why does the LSTM hit 0.99 on synthetic but only 0.81 on real data?
  Two reasons. The synthetic generator injects fraud as a clean, separable
  behavioral burst, so it's almost trivially detectable. Real IEEE-CIS fraud is
  subtle AND our adapter only used ~9 of 394 columns — we discarded the C/D/V
  engineered features that carry most of the signal. Plus IEEE-CIS is
  per-transaction with a weak user proxy (median 2 txns/user), so the sequence
  model has little structure to exploit. It's a features/data-framing gap, not a
  model-capacity gap — which we proved by training a quick LightGBM that beat the
  LSTM by 7+ AUC points.

Q6. Why combine LightGBM and the LSTM instead of picking one? Why stacking?
  They capture complementary signal: LightGBM is the strongest tool for the rich
  TABULAR features; the LSTM adds the sequential signal LightGBM can't see. We
  combine with a stacking meta-learner (logistic regression over the two models'
  scores) rather than a fixed average so the WEIGHTS ARE LEARNED from data. We fit
  the meta-learner on the validation split to avoid leakage. The hybrid beat
  LightGBM alone, confirming the LSTM contributes real, non-redundant signal.

Q7. How do you align a per-transaction LightGBM with a per-user LSTM for stacking?
  The prediction unit is the user/sequence (the label is "fraud anywhere in the
  user's last-50 window"). LightGBM scores each transaction; we aggregate those
  to one score per user with MAX (a user is risky if any transaction is). The LSTM
  already outputs one score per user. We align both onto the LSTM's user ordering,
  filling any missing LightGBM user with the median, then stack.

Q8. AUC-ROC is your headline metric. Is it the right one for 3% fraud? What else?
  AUC-ROC is threshold-independent and good for ranking, but it can look optimistic
  under heavy imbalance because the negative class dominates the FPR axis. So we
  also track AVERAGE PRECISION (area under precision-recall), PRECISION AT A FIXED
  LOW FPR (e.g. <= 5%), and dollar metrics (net savings). For deployment the
  operating threshold matters more than AUC, so we tune it explicitly.

Q9. Your threshold tuning produced precision 1.0 but recall ~0. What happened, fix?
  "Maximize precision subject to FPR <= 5%" can collapse to an extreme threshold
  that flags only the single most-confident case (precision 1.0, recall ~0). It's
  a degenerate corner of the constraint. We surfaced it and added a profit curve
  (net savings vs threshold) so we pick the operating point on business value, and
  we'd cap minimum recall or optimize expected cost directly in production.

Q10. Explain the OpenMP segfault and your fix.
  PyTorch and LightGBM each bundle their own OpenMP (libomp) runtime. Loading both
  into one process on macOS causes two OpenMP runtimes to coexist, which
  deadlocks/segfaults. It was hidden because no single test imported both. The
  hybrid trainer needs both, so we set OMP_NUM_THREADS=1 and
  KMP_DUPLICATE_LIB_OK=TRUE BEFORE importing either library, single-thread both,
  and added a subprocess regression test (isolated so a crash can't fail the whole
  suite). Import order alone didn't fix it; constraining threads + the env flag did.

Q11. Why output logits and use BCEWithLogitsLoss instead of a Sigmoid + BCELoss?
  BCEWithLogitsLoss fuses the sigmoid and the loss in a numerically stable way
  (log-sum-exp trick), avoiding overflow/underflow and vanishing gradients at
  saturated probabilities, and it's where pos_weight is applied cleanly. So the
  model emits raw logits during training and we apply sigmoid only at inference
  (predict_proba). The reference architecture had a trailing Sigmoid; we
  deliberately removed it for this reason.

Q12. How does drift monitoring trigger retraining? Why PSI and why those features?
  We compute Population Stability Index (PSI) between a reference window and the
  recent window for three behavioral features (txn_velocity_1h, amount_zscore,
  new_device_flag). PSI bins the reference distribution and measures how much the
  current distribution has shifted; PSI > 0.20 on any monitored feature triggers
  retraining and a Slack alert. We chose those three because they're the
  highest-signal behavioral features and directly reflect the takeover pattern;
  monitoring a focused set keeps the signal clean and the alert noise low.

Q13. What is champion/challenger and how does promotion work?
  The current production model is the "champion." A newly trained "challenger"
  must pass TWO gates before promotion: (1) an absolute MLflow AUC gate (>= 0.90,
  no manual override), and (2) it must BEAT the champion's AUC (optionally by a
  margin). In production it also gets shadow/A-B traffic (e.g. 10%) before full
  promotion. We implemented decide_promotion() combining both rules and share it
  between the local pipeline and the Airflow DAG so they can't disagree.

Q14. Why left-pad sequences and mask, rather than right-pad?
  Left-padding puts the MOST RECENT transaction at the last position for every
  user, so "position" has consistent temporal meaning regardless of history
  length, which helps the model and the attention readout. The padding mask
  ensures the LSTM/attention ignore the zero rows so short histories aren't
  polluted by fake "transactions." (For the LSTM we also avoid letting padding
  contribute to the attention-weighted context.)

Q15. How would you deploy this and hit p99 < 50ms? What are the risks?
  Package model + scaler + threshold + inference code into model.tar.gz, deploy as
  a SageMaker real-time endpoint with the four handlers (model_fn/input_fn/
  predict_fn/output_fn). Benchmark p50/p95/p99 under load; if p99 > 50ms, reduce
  sequence length, shrink hidden size, TorchScript/compile the model, or move to a
  compute-optimized instance. Keep train/serve parity by shipping the SAME fitted
  scaler. Risks: feature computation latency (velocity windows) can dominate, so
  precompute/caching matters; cold starts; and the hybrid adds a second model +
  meta-learner to the critical path, which you'd co-locate or precompute.

Q16. The card1+addr1 user_id is a proxy. What are the dangers and alternatives?
  It's imperfect: collisions (a popular card1 with missing addr1 collapses many
  real users into one mega-"user" with thousands of transactions), and most real
  users get only 1-2 transactions, starving the sequence model. Dangers: label
  contamination on collision buckets and weak sequence signal. Alternatives used
  in IEEE-CIS solutions: a stronger uid (card + addr + a D1-derived registration
  day), or accept that the dataset is per-transaction and lean on the tabular
  model. In production you'd use a real account/customer id and the sequence model
  would be far stronger.

Q17. (Stretch) How would you push from 0.929 toward the 0.94 target responsibly?
  The remaining levers are uid-aggregation features (per-user TransactionAmt
  mean/std/count, inter-arrival stats) and D-feature day-normalization — the
  highest-impact IEEE-CIS techniques. The catch: done as GLOBAL aggregations they
  LEAK; done correctly you compute stats on the train split only and map them
  forward, with a cold-start fallback for unseen users. We made the deliberate
  call that 0.929 is strong and the last point wasn't worth dataset-specific,
  leak-prone engineering — a real-world tradeoff judgment, not just a number chase.
